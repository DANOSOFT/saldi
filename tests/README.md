# Tests

Three layers, all runnable against the repo's own docker-compose stack.

| Layer | Where | What it covers |
|---|---|---|
| Characterization | `tests/characterization/` | The posting engine, VAT, open posts, dunning, the order lifecycle and stock — driven through the real page scripts and `includes/ordrefunc.php`, against a real tenant database. |
| REST API | `tests/restapi/` | `restapi/` over HTTP: authorization on every endpoint, plus CRUD and pagination on the ones that write. |
| End to end | `e2e/` | A browser: login, posting a voucher, and every module's landing page. |

## Running them

The stack must be up and Saldi must be installed. From a fresh clone:

```bash
docker compose up -d
tools/ci/bootstrap-stack.sh          # install wizard + accounting entity
```

Then:

```bash
docker compose exec -T -w /var/www/html/saldi web php vendor/bin/phpunit
```

```bash
npm ci && npx playwright install chromium
node e2e/seed-user.mjs
npx playwright test
```

`.github/workflows/tests.yml` does exactly this on every pull request.

## Why the DB-backed tests skip instead of fail

`includes/connect.php` is generated by the install wizard and is gitignored, so
a bare checkout cannot serve a page. Rather than fail there, the suites detect
a missing stack and skip, which keeps `composer test` green on a machine that
has never run docker. The cost is that a CI job which forgets the bootstrap
step reports "OK" having run almost nothing — hence the bootstrap script.

## A note on pinned defects

Some tests assert behavior that is wrong. They say so, in a docblock naming
the file and line, and they exist so the wrongness cannot change unnoticed.
When one fails, that is the fix landing: rewrite it to assert the correct
behavior. `doc/TESTING_FINDINGS.md` lists all of them.
