# Package entitlements: observation rollout, 25 November 2026

This is the first implementation against the owner's package breakdown of 24 November. It is based on the ssl12 integration branch (`asr/saldi-integration-20261124`, PR #1199). It starts in **observe mode**. It is not an approval to enable enforcement or deploy to production. The coverage gaps below must be addressed before enabling the affected features.

## Authoritative data

`regnskab_entitlements` in the master holds each account's package, catalogue version and enforcement mode. Signup writes this row in the same transaction as its master account reservation. A failed tenant creation removes its reserved entitlement along with the account. Existing `regnskab.pakke` values are copied once where no assignment exists; runtime no longer reads that column. Manually created accounts without a package acquire no package restrictions.

`config/entitlements.json` contains the provisional seed, aliases, feature dependencies and add-on grants. Package availability is read at runtime from `plan_features`; numeric limits come from `plans.max_users`, `plans.included_postings`, `plans.max_items` and `plan_limits.max_webshops`. SQL NULL means unlimited; zero means none. Existing operator overrides and their expiry dates still apply. Changing catalogue rows or account overrides affects the next request, without editing page logic. Changes after the 1 December meeting should update the catalogue data and the corresponding seed for new installations.

`entitlement_schema()` runs at the end of `betweenUpdates.php`, after the existing operator-panel schema, and during new installation. It uses the master connection, a named migration lock and a checked data transaction. The revision flag is written last. Re-running a completed revision preserves subsequent operator edits. Existing prices and explicit overrides are retained. This revision sets every existing package assignment to observe and creates new assignments in observe. Before the migration is ready, runtime adds no gates; signup asks for the installation update rather than creating an account without its assignment.

## Runtime and current coverage

- `ent_allows(feature)` reports the effective entitlement, even in observe mode. `ent_limit(key)` returns an integer or NULL. Pages use `ent_check()` / `ent_check_limit()` so observe mode logs instead of refusing.
- `perm_enforce_request()` applies the package ceiling independently of the tenant's role enforcement switch. Dedicated page checks cover budget, recurring invoicing, reminders, Betalingsservice, e-invoice sending, price/discount groups, stocktaking, stock transfers, min/max, receiving scan lists and picklists. Dedicated settings sections are covered too.
- The existing `lager.varer`, `kreditor.ordre`, `lager.varemodtagelse` and `pos.kasse` permission keys have package checks. Read-classified inventory/purchase requests remain available after downgrade. Supplier posting is explicitly exempt. Shared screens still require the action audit in the next section.
- Ordinary invoicing, journals, accounts, customers, suppliers, voucher storage, VAT/EU reporting, year close, reports and export paths have no new package gate. Generating an invoice export remains available; sending it through the e-invoice service has its own entitlement.
- Browser login measures distinct active usernames on the master, excluding auditors, expired sessions and the reconnecting username. It uses the existing four-hour activity window. When enforcement is enabled, a named lock spans the count and session insert. The cap is concurrent users, not the number of user records; the operator's live usage view uses the same measure. Historic snapshots still count user records and are not used for concurrent-user quota warnings.
- Posting volume is measured on login using `transaktioner.logdate` over the last twelve months, matching the existing operator usage definition. The owner confirmed the rolling twelve-month period on 25 November 2026. Crossing the volume allowance logs an observation and never blocks bookkeeping. No automatic charge or billing change is introduced.
- Finans has the data feature `sales.quick_invoice_required`. Its effective DIV/3 box4 value is forced on only in enforce mode, in the order list, order screen, delivery and settings readers/writers. Observe mode leaves the stored value and workflow unchanged. The Diverse user-limit writer is also observed first and refuses customer changes only in enforce mode.
- POS, booking and commission use their module entitlements. Webshop add-ons are checked at the legacy shop-order API, authenticated REST module writes, webshop settings, item sync entry and the common shop import/stock transport functions. A refused automatic stock sync returns without preventing the invoice from posting. Read-only REST requests remain available under the normal role rules.
- Blocked browser requests show an upgrade message and price-page link; JSON endpoints return `upgrade_required` with HTTP 403. All exits happen before the gated operation.

## Remaining work before enforcement

1. **Mobile voucher scanning:** `bilag.scan_mobile` is in the catalogue, but the service at `ai.saldi.dk/invoice-extraction/` is maintained outside this repository. Its authenticated server boundary needs the same entitlement check. The source repository has been requested. The ordinary voucher pool remains core.
2. **Phase 2:** item quantity across all creation/import/API paths, offers/backorders within the shared order screen, purchase approval, dimensions, serial numbers and batch. Their catalogue data is present; this change does not claim to enforce those shared actions. GET requests classified as read by legacy pages also need that action audit; a new-item editor must not be mistaken for a completed quota check.
3. **Counts and shared add-on controls:** webshop count limits are represented as data, but not enforced at every connection writer. POS location selection, warehouse creation/counts and commission/booking operations embedded in other modules need their action-level checks. The dedicated module entry checks do not replace these.
4. **Warehouse agreement:** no warehouse quantity is chosen. Business's included count and whether Professionel may buy an extra warehouse remain undecided. Stock-transfer access follows the Business feature; it does not decide the extra-location allowance.
5. **Other admission paths:** the concurrency gate covers the ordinary browser login. Operator impersonation remains available for support. Separate API token/service sessions are not counted as browser users. Review any external or alternative customer-login path before enabling that cap.
6. **Commercial assignment:** this change connects website signup, existing saved signup packages and operator assignments. It does not infer a package from historical invoices or create a new billing/Stripe integration. Verify existing customers' assignments and paid add-ons against their agreements before enforcement; an unassigned account intentionally remains open.

## Reading the observations

Server PHP logs receive a `[entitlement]` prefix followed by JSON containing event, account id, package, feature/limit key, mode, script, method and counts where relevant. Events include `entitlement.would_deny` and `entitlement.would_force`; actual enforcement uses `entitlement.denied` and `entitlement.forced`. Query strings, credentials and document contents are not recorded. Browser observations are deduplicated per day, session, account, feature, script, method and event; API observations are deduplicated within the request.

Review unexpected denials by account and feature, check the catalogue/add-on allocation, and compare the attempted operation with the customer's agreement. There is no automatic transition from observation to enforcement. No customer settings form can switch `regnskab_entitlements.enforcement`.
